# notes-consolidator 自进化记录（EVOLUTION.md）

> 本文件记录该 skill 的"自进化"全过程：每一轮由**测量数据**驱动下一轮改动，
> 体现 Week14「自进化 Agent」课程主题 —— Agent 不是一次写死 skill，
> 而是通过执行—测量—反思—改写 的闭环持续改进自己的技能。

---

## 轮次总览

| 版本 | 单次任务 token 合计 | 脚本耗时 | 唯一内容丢失 | 近似重复未合并 | 状态 |
|------|--------------------:|---------:|------------:|---------------:|------|
| v1（初版） | 2814 | 0 ms（无脚本） | 0 | 0 | 基线：质量好、成本高 |
| v2（第 1 轮优化） | 2602 | ~25 ms | 0 | **2** | ⚠️ 成本略降、质量回退 |
| v3（第 2 轮自进化） | **1141** | ~72 ms | 0 | 0 | ✅ 成本大降、质量恢复并由校验保证 |

测量口径：SKILL.md 指令 token + LLM 输入 token + LLM 输出 token（tiktoken/cl100k_base），
语料固定为 data/raw_notes.md（934 tokens）。

## Round 0：模型编写初版 skill（v1）

**动作**：让大模型从零编写 notes-consolidator（学习笔记整理器）——
把零散、重复的中文笔记整理成结构化、去重、无损的 Markdown。

**v1 的设计**：纯 LLM 方案。SKILL.md 用大段文字描述 4 步流程（读全文 → 分析结构 →
合并去重 → 输出），并附 Q&A 与示例。LLM 每次调用需读取**全部原文**，再**重写整份文档**。

**测量结果**（benchmark.py）：
- SKILL.md = 1194 tokens（说明冗长，每次调用固定开销大）
- 输入 = 934 tokens（全文进上下文）
- 输出 = 686 tokens（整份整理稿由 LLM 生成）
- 合计 **2814 tokens / 次**，LLM 估算耗时 ~3.4s
- 质量：0 丢失、0 重复残留（LLM 语义判断力强）

**反思**：质量没问题，但成本高。两个浪费点：
1. 机械性工作（找完全重复、数行数、切章节）也由 LLM 用 token 完成；
2. SKILL.md 说明冗长，固定开销大。

**决策**：第 1 轮优化 → 把机械性工作下沉到本地脚本。

## Round 1：第一轮优化（v2）

**动作**：新增 `consolidate_v2.py`（按标题切分章节、检测完全重复、生成 plan.json），
SKILL.md 精简为"运行脚本 → 读 plan → 输出"（342 tokens，-71%）。

**测量结果**：
- SKILL.md = 342 tokens（✅ -71%）
- 输入 = 1432 tokens（❌ 反而比全文 934 还大！）
- 输出 = 828 tokens
- 合计 2602 tokens（仅 -7.5%），脚本 ~25 ms
- 质量：**近似重复未合并 = 2 对**（❌ 质量回退）

**反思（两个问题被测量暴露）**：
1. **plan 膨胀**：plan.json 把全部"唯一内容"又包装了一层 JSON（键名、缩进、重复文本），
   LLM 输入不减反增 —— "把工作给脚本"只解决了 SKILL 开销，没解决输入开销；
2. **近似重复漏检**：脚本只做"完全重复"检测。语料中两处"意思相同、用词不同"的段落
   （相似度 0.78 / 0.87）没有被标记，LLM 也没有被要求处理 → 输出保留 2 对重复段落。

**决策**：第 2 轮自进化 →
1. plan 改为**精简版**：只含需要 LLM 判断的内容（章节清单 + 近似重复对），正文不进上下文；
2. 脚本新增**模糊去重**（difflib 相似度 ≥ 0.72 判为近似重复）；
3. 新增**决策式组装**：LLM 只输出合并决策 decisions.json（每对选 a/b），
   最终文档由脚本从原文**确定性组装**，输出 token 与格式问题一并解决；
4. 新增 **--verify 无损校验**：把"质量"变成可自动验证的门禁，防止再次回退。

## Round 2：第二轮自进化（v3，当前版本）

**动作**：按 Round 1 的决策重构（consolidate.py），SKILL.md 重写为 5 步精简流程。

**测量结果**：
- SKILL.md = 496 tokens（✅ 比 v1 省 58%）
- 输入 = 489 tokens（✅ 比 v1 的 934 省 48%；比 v2 的 1432 省 66%）
- 输出 = 156 tokens（✅ 比 v1 的 686 省 77% —— 只输出决策，不再重写整篇）
- 合计 **1141 tokens（✅ 比 v1 省 59.4%）**，脚本 ~72 ms（毫秒级，可忽略）
- LLM 估算耗时 3.4s → 1.4s（-59%）
- 质量：**0 丢失、0 重复残留，--verify ✅ 无损**

**自进化结论**：
- v3 用 v1 的 **40% token** 达到同等质量，且质量由 `--verify` 门禁保证，
  不会再悄悄回退；
- 演进不是一次到位的：v2 看似"优化"实则质量回退，是靠测量 + 门禁发现的；
  这正是自进化 Agent 的价值 —— 每轮都基于证据改进。

## 附录：为什么 plan 必须"精简"（本轮踩坑记录）

v3 第一版 plan 也踩了 v2 的坑：为每个章节附了 `first_line` 预览与冗长说明，
结果 plan 高达 1479 tokens，只比全文略小。测量发现后立即删除预览字段、
压缩 JSON、把"完全重复"改为只报数量（脚本自动删，无需 LLM 判断），
plan 降到 489 tokens。**结论：plan 的大小必须与"需要判断的量"成正比，
而不是与正文大小成正比。**

## 附录二：大语料验证时发现并修复的组装边界 bug（Round 2.5）

给 `raw_notes_large.md` 做扩展性验证时，`--verify` 报"唯一内容丢失 3 处"：
语料里"忠实度衡量…"这句同时是【完全重复】（评估指标 vs 重复片段）与
【近似重复对】的成员（pair3 的 b 侧）。旧组装逻辑在"一侧已被完全重复机制移除"
时会把另一侧也误删（`pos_b != pos_a` 分支无条件删除）。

**修复**：两侧都存在才做"替换+删除"；只剩一侧时原样保留。
修复后大语料 ✅ 无损，小语料回归测试 ✅ 无损（没有修坏）。
**启示**：自进化要防"修 A 坏 B"——每轮改动都要跑回归（`--verify` 双语料）。
